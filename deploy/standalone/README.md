# Private standalone deployment

This deployment packages the current HappySpa Life OS frontend and the
personal-workbench API module in this folder. It does not proxy page/API traffic
through the HappySpa Worker and does not connect to D1. Only the authenticated
40-collection private Life OS export can be imported.

## Runtime and boundaries

- Caddy owns HTTPS ports 80/443 and forwards traffic to the app container.
- The Node adapter serves a unified account login shell (`username` + `password`,
  no self-signup) and verifies the signed `happyspa_personal_workbench` cookie.
  It keeps the existing `/workbench` route, legacy entry-key exchange, eight hour
  expiry, key-version invalidation and `Secure; HttpOnly; SameSite=Strict` cookie
  properties. Legacy entry-key sessions remain account A's Life OS access only.
- `/workbench/api/*` maps to the extracted current private Life OS handlers;
  `/projects` uses the compatibility endpoint and `/analytics` maps to
  `/insights`. The handlers run against an SQLite adapter implementing D1's
  `prepare/bind/first/all/run/batch` calls.
- SQLite migrations 0070–0095 contain only private-workbench/Life OS tables plus
  the additive `platform_*` identity/authority tables, including source project
  IDs, workspace layout, owner credential state, audit tables, durable
  per-token logout revocations, the recurring-task idempotency ledger, and the
  additive MVP task-card/Worker-routing tables and the additive research
  state-machine and Obsidian outbox tables. No store schema or `config` table is
  created.
- The app container publishes no host port. Caddy is the only public container.
  The application refuses to start without `AUTH_SECRET` and
  `PERSONAL_WORKBENCH_ENTRY_KEY`.
- The app trusts forwarded HTTPS headers only from Caddy's fixed private
  `172.31.88.2` address and requires the configured `LIFEOS_PUBLIC_ORIGIN`.
  The proxy network is isolated from the optional AI service network.
- The recurrence runner is off by default. Leave
  `LIFEOS_RECURRENCE_ENABLED=false` through import and first acceptance so
  preserved completion history cannot trigger duplicate scheduled tasks. Enable
  it explicitly only after comparing the imported recurrence ledger.

## Build

Build the `linux/amd64` image on GitHub Actions or a sufficiently large build
host. The 2 GiB ECS should run the prebuilt image only.

```sh
docker buildx build --platform linux/amd64 --load \
  -f Dockerfile --build-arg LIFEOS_BASE_PATH=/workbench \
  -t lifeos-standalone:local .
```

The verification workflow also publishes a short-retention artifact containing
the tested `linux/amd64` app image, the AI service image, and their SHA-256
manifest. It also contains `lifeos-standalone-node.tar.gz`, a Node 24 bundle
with the Next standalone build, static/public files, API runtime, and SQLite
migrations; it does not require Docker. The adjacent `.sha256` file hashes the
archive, `lifeos-images.sha256` lists all three build archives, and the bundle's
`MANIFEST.sha256` checks every packaged file. Download the artifact named
`lifeos-standalone-<commit>` and verify both archive and internal manifest.
Run `sha256sum -c lifeos-images.sha256` and
`sha256sum -c lifeos-standalone-node.tar.gz.sha256`, then run
`sh deploy/standalone/scripts/loopback-acceptance.sh
/path/to/lifeos-standalone-node.tar.gz` on a Node 24 host before using it.

For a service deployment behind an already configured HTTPS reverse proxy,
extract the archive, provision a private persistent data directory, set the
existing private session secret and entry key plus `LIFEOS_PUBLIC_ORIGIN` and
`TRUSTED_PROXY_IP`, then run `sh deploy/standalone/scripts/run-node.sh`. It
binds to `127.0.0.1` by default. No credentials are included or generated by
the deployment launcher. Keep recurrence off through initial data acceptance.

To use the Docker build instead, download the artifact, verify the hashes, load
the app tar and tag it `lifeos-standalone:local`. Only load and tag
`lifeos-agent:<commit>` as `lifeos-agent:local` if enabling the AI profile.

Copy `.env.example` to `.env` on the server and supply `LIFEOS_DOMAIN`,
`AUTH_SECRET`, and `PERSONAL_WORKBENCH_ENTRY_KEY` from the approved private
secret source. Keep these values and any data exports outside the public repo.
Set DNS and allow ports 80/443 through the normal deployment process. Then run
`docker compose up -d` in this directory. Caddy provisions HTTPS; the app and
SQLite database remain private to the compose network.

## Unified login and platform admin

First-version unified login adds account A as the legacy Life OS owner/platform
admin and lets A create regular accounts and grant configured internal
workspaces. Account B cannot see any A data or any ungranted workspace. Security
principals are the immutable `platform_accounts.account_id` and
`platform_workspaces.workspace_id`; usernames and slugs are never owners.

Additive migration `0092` is applied once on startup and is rerunnable. It seeds
only the deterministic Life OS workspace; the owner account is bound at startup
from `PERSONAL_WORKBENCH_OWNER` and is password-free (no account B, no secret).
Additive migration `0093` stores only SHA-256 digests of revoked session tokens
so logout is durable and per-token, not just a cookie clear.
Additional internal workspaces are operator metadata via `PLATFORM_WORKSPACES_JSON`
and stay in a safe not-configured state until an implementation target is set.
Auth/account/grant/session/audit metadata is excluded from the 40-collection Life
OS export/import/reset contract. See
[docs/platform-auth-migration.md](docs/platform-auth-migration.md) for the apply,
rollback, owner-mapping, credential-entry and workspace configuration details.

## Task cards and Worker routing

The MVP task-card slice adds durable card metadata (type, goal, expected
artifacts, existing subtask/dependency ids, three role assignments, verification
evidence, next step) for an existing Life OS task id, plus Worker routing by
`type + role`. Both are served by the standalone module under
`/workbench/api/task-cards/*`, are scoped by account + workspace + task, and
require the stable legacy owner principal (`isLegacyOwner`) plus the exact
`ws_lifeos_legacy` grant; routing writes require the current platform-admin
policy. The Worker catalog is server-side, supports DeepSeek and OpenAI, labels
Gemini as unavailable, exposes no credentials, and the UI never calls a provider.
See
[docs/task-card-worker-routing.md](docs/task-card-worker-routing.md).

## Data migration and recovery

Export from the authenticated current endpoint
`/api/personal-workbench/lifeos/data/export` to a private encrypted location.
After first startup applies the isolated schema, run
`./scripts/import-happyspa-export.sh /absolute/path/export.json`.

The importer requires all 40 export arrays and no unknown fields, preserves
ISO date strings and source project IDs, remaps task/project references,
checks per-table counts and foreign keys, and commits atomically. It excludes
owner credentials and session state, which must be configured separately.
Audit logs, generic workbench project/checkpoint data, and recurrence execution
history are included. The export scope contains only private-workbench and
Life OS tables; it excludes all HappySpa store data. A non-empty target is
refused. The importer prints per-collection counts for comparison with the
source export.

Use `scripts/backup.sh`, `scripts/verify-backup.sh` and the guarded
`scripts/restore-db.sh` for separate private backups and recovery. The restore
requires `LIFEOS_RESTORE_CONFIRM=YES`, validates its source, saves a verified
pre-restore copy, and atomically replaces the SQLite file while the app is
stopped.

## Offline verification

```sh
node scripts/test-runtime.mjs
node scripts/test-http.mjs
node scripts/test-platform-migration.mjs
node scripts/test-platform-http.mjs
python3 scripts/test-sqlite-tools.py
sh scripts/loopback-acceptance.sh /path/to/lifeos-standalone-node.tar.gz
```

These verify schema migration, session signature/expiry/key-version checks,
app-state optimistic concurrency, project/task persistence, current export
import/count/FK checks, HTTP login/auth/error behavior, and backup/restore
behavior. The platform tests additionally cover migration idempotency, the
legacy owner mapping, account/workspace/grant authority and immediate session
invalidation, durable per-token logout revocation (account, legacy, old-format
and isolated-session cases), the auth/export boundary, append-only audit, and
account B's denial across every private Life OS prefix/alias, agent endpoints,
and header/origin/host spoof attempts. `test-http.mjs` and
`test-platform-http.mjs` need loopback sockets. A container build, real HTTPS
browser run, real export comparison, and ECS memory measurement remain
deployment acceptance gates.

## Optional AI planning service

The private task planner is integrated as an opt-in `ai` Compose profile. It
uses a dedicated PostgreSQL volume and separate service/worker containers; it
does not access the Life OS SQLite database or HappySpa data. The app gateway
forwards only the signed-in owner's explicit task prompt over a server-side
HMAC subject bridge. There is no direct public route to the service. The UI
creates a draft first, shows its exact prompt/model/budget, and requires a
separate approval click before the worker can call a provider. Results are
proposals and never update tasks automatically.

On the 2 GiB ECS, keep this profile off unless memory is measured with the
complete workload. To enable it, configure the database password, random
service token, independent signing secret, provider key and current pricing
rates in the private `.env`; then run
`docker compose --profile ai up -d`. Do not use sample or empty credentials.
The endpoint stays disabled until both provider configuration and a recent
worker heartbeat are present. OpenAI requires its own additional confirmation.
Back up its separate database with `scripts/backup-agent-db.sh`; retain the
dump and SHA-256 file privately.

No AI provider credentials are bundled. Without the optional profile and
credentials, core Life OS remains usable and AI reports itself unavailable.

## Research state machine and Obsidian sync

The private Life OS research surface (`/api/research/*`) persists a bounded
research state machine and a deduped evidence store. There is no Neo integration
or research scheduler in this repository, so an explicit start only persists
`waiting_executor` ("等待 Neo/研究执行器连接"); it never reports `running`, never
schedules background work and never calls a provider. Server-owned execution
caps bound the budget, frequency, source/action allowlists and the
concurrent/subtask limits, and client-reported spend is never accepted. The
budget is a finite positive cap ($1, matched to the Agent Service default);
zero/negative is rejected and there is no "0 means unlimited". Source/action
choices come from server-owned immutable option catalogs (abstract and inert,
with no web fetch or model action), the minimum check interval is 60 minutes,
and at most one subtask runs concurrently in this first slice.

Obsidian sync is disabled/unconfigured. Vault root/subfolder permission is still
pending, so no filesystem configuration is wired and no file is ever written:
the endpoint only stages user-reviewed incremental artifacts into a separate,
scoped outbox as `pending_sync`, read back per task through
`/tasks/:taskId/obsidian/status`. Research history is append-only: there is no
plan-delete endpoint and no replan-erasure. The adapter contract (explicitly
selected folder, bounded append-only block, base-hash conflict without
overwriting) is defined and tested with an in-memory fake only. See
`docs/research-obsidian-sync.md`.
